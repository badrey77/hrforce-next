# ADR 008: Document generation — Typst in the API, stored PDFs, gap-free numbering in Postgres

**Status:** Accepted (owner, 2026-09-28)
**Date:** 2026-09-28

(ADR 007 is reserved for SSO.)

## Context

M3 starts with numbered HR documents generated by the API (owner decision, 2026-09-28; contract
`docs/contracts/documents.md`): attestation de travail, certificat de travail, titre de congé, in **French and Arabic**,
with the company letterhead and a signatory, numbered per company and per type without gaps, and kept in a register
where a reprint returns the same document.

Constraints that shape the choice:

- **ADR 005:** Postgres is the only stateful dependency. No object storage, no external service, no SaaS renderer.
- **Offline sites / Law 18-07:** nothing may be fetched from the internet at runtime; fonts are self-hosted (owner
  decision 2026-09-26: **Cairo** for Arabic, **Source Sans 3** for Latin). The web gets them from
  `@fontsource-variable/cairo` and `@fontsource-variable/source-sans-3` (`apps/web/src/styles.css`), but those are
  **WOFF2 subsets of the variable fonts** (`cairo-arabic-wght-normal.woff2`, `…-latin-…`), which PDF engines generally
  cannot embed as-is. The API needs its own TrueType files.
- **Arabic must be right:** contextual shaping (joining forms, lam-alef ligatures), the Unicode bidi algorithm for mixed
  runs (a Latin matricule, digits, dates and parentheses inside an Arabic sentence), RTL paragraph alignment and
  justification. A document that gets this wrong is unusable, and it is the part most PDF libraries get wrong.
- **Deploy (ADR 005, `apps/api/Dockerfile`):** one image, `node:22-alpine` (musl), read-only root filesystem with a
  `/tmp` tmpfs, non-root user, `npm ci --ignore-scripts`. Developers work on Windows (`scripts/dev-up.ps1`) and CI on
  Ubuntu; the renderer must install from the lockfile on all three.
- **One transaction per request (ADR 001):** the number, the register row and the file must commit together.

## Options evaluated

## Evidence (prototype, 2026-09-28, outside the repo)

A scratch project rendered an **attestation de travail** in Arabic and in French from a JSON snapshot, with
`@myriaddreamin/typst-ts-node-compiler@0.7.0`, inside `node:22-alpine` (the production base image) and natively on
Windows. The Arabic body mixed an Arabic name (وليد منصوري), a Latin matricule (`EMP-0042`), dates (`14/03/1988`,
`01/09/2019`), a Latin job title in parentheses (`(Ingénieur systèmes)`), an amount (`85000.00 دج`) and the number
`ATT-2026-00042`; the French body contained the Arabic name in parentheses.

Checks:

1. **Visual** — pages rasterised with PyMuPDF (MuPDF 1.28) to PNG and inspected: Arabic letters joined correctly
   (initial/medial/final forms, the lam-alef ligature in «الإنجاز»), right-aligned and justified paragraphs, Latin and
   digit runs kept left-to-right inside the Arabic sentence, parentheses mirrored correctly around the Latin run, the
   RTL grid put the letterhead on the right and the number on the left; the French page rendered the embedded Arabic
   name correctly inside the LTR paragraph.
2. **Text extraction** — `pdftotext -enc UTF-8` returns the Arabic text in logical order with the right letters (the
   ToUnicode maps are correct, so the PDF is searchable and copy-pastable).
3. **Fonts** — only the subsetted vendored fonts are embedded (`Cairo-Regular`, `Cairo-Bold`, `SourceSans3-Regular`,
   `SourceSans3-Bold`).
4. **Determinism** — the same snapshot produced **byte-identical PDFs** across runs, across processes, and across
   **Windows (win32-x64) and Alpine (linux-x64-musl)** (same SHA-256), once the document date is fixed from the
   snapshot (`set document(date: …)`, no wall clock).
5. **PDF/A-2b** — `pdf({…}, {pdfStandard: 'a-2b'})` produced a PDF/A-2b file (XMP `pdfaid:part 2`,
   `conformance B`, output intent) including a PNG logo passed from memory (`mapShadow`). PDF/A requires a document
   date: we set it to the issue date.
6. **No template injection** — a signatory name of `#panic("pwned") *bold* $x^2$ #read("/etc/passwd")` passed as data
   printed literally: values read from `sys.inputs` (JSON) are strings, never evaluated as Typst markup.
7. **Speed / memory** — ~4–15 ms per page once warm (the first compile in a fresh process ~200 ms, font loading);
   process RSS ~95 MB after 50 renders in the container (Node alone ~45 MB).
8. **pdfkit comparison** — the same Arabic paragraph through pdfkit 0.17 had shaped glyphs but broken bidi: words of
   each line in the wrong order, «EMP-0042،» and «(Ingénieur systèmes)» displaced, punctuation at the wrong end.

## Decision

1. **Renderer: Typst**, through `@myriaddreamin/typst-ts-node-compiler` (exact version pinned; the embedded Typst
   version is recorded with every document). It lives behind a platform port `PdfRenderer`
   (`apps/api/src/platform/pdf/`): `render({template, input, assets, standard}) → Buffer`. The port hides the engine,
   so moving to the Typst CLI (child process) or Chromium later changes one adapter.
   - Rendering runs in a **dedicated child process** per API process (amended 2026-10-02, see below; first a
     `worker_threads` thread). The binding's `pdf()` is synchronous native code: it must not block the event loop,
     nor take the API down when it faults. There is a queue and a **timeout of 15 s** (→ 503 `document-render-failed`).
     One compiler instance per process, created at first use; fonts passed as in-memory blobs (`fontBlobs`, no
     directory scan, no system fonts).
   - Output: **PDF/A-2b**, A4, document date = the issue date, title/author set, no wall-clock timestamp.
   - Data reaches templates **only** as one JSON string in `sys.inputs` (strings are never evaluated as markup);
     binary assets (the company logo) through `mapShadow` under a per-company virtual path.
2. **Fonts: vendored static TTF instances** in `apps/api/assets/pdf/fonts/`: `Cairo-Regular.ttf`, `Cairo-Bold.ttf`
   (wght 400/700, slnt 0), `SourceSans3-Regular.ttf`, `SourceSans3-Bold.ttf`, instantiated from the SIL OFL variable
   fonts of the Google Fonts repository (`ofl/cairo/Cairo[slnt,wght].ttf`, `ofl/sourcesans3/SourceSans3[wght].ttf`)
   with fontTools `varLib.instancer`; `OFL.txt` files and a `README.md` recording the source commit and the command
   sit next to them (~1.1 MB total). Arabic documents use Cairo first and Source Sans 3 as fallback; French documents
   the reverse. The web keeps its own WOFF2 files — same families, different packaging.
3. **Templates: in code, one Typst file per document type** (`apps/api/assets/pdf/templates/<type>.typ`, plus a shared
   `letterhead.typ`), reviewed like code, each with a version string (`attestation_travail@1`) stored with every
   document; changing wording bumps the version. The **legal wording is fixed per type and language**; what a company
   edits is **data**: letterhead (legal names fr/ar, address, identifiers NIF/NIS/RC/AI, phone, e-mail, logo, footer),
   signatories (name and title fr/ar), number format, active types. User-editable templates are **not** offered:
   Typst is a programming language, and user-authored code in the API process (loops, huge allocations) is a denial
   of service we would have to sandbox; it can be revisited with a restricted block editor if the owner needs custom
   wording.
4. **Snapshot first, render second.** Issuing builds a **snapshot**: the exact JSON the template receives, with every
   string already formatted (localised dates with Algerian month names in Arabic — جانفي، فيفري، … ; Western digits in
   both languages; names with Arabic fallbacks), plus the ids it came from. Formatting is pure domain code, unit
   tested; the template does layout only. `PDF = render(templateVersion, snapshot, fonts, logo)`.
5. **Storage: store the PDF bytes, and the snapshot beside them.** `issued_document` (audited metadata incl. the
   snapshot, the SHA-256 of the PDF, the template and renderer versions) + `issued_document_file` (`pdf bytea`,
   insert-only, exempt from the row-diff audit, integrity via the audited hash). Reasons:
   - a reprint must be **identical**; the prototype shows determinism *for a given engine, template and font set*, but
     any upgrade of Typst, the binding, a font or a template changes bytes — regenerating old documents would oblige us
     to keep every historical engine and template runnable forever;
   - the bytes are small (**20–30 KB** per page with subsetted fonts): 10 000 documents a year ≈ 300 MB;
   - Postgres `bytea` keeps RLS, transactions and backups (ADR 005); large objects are rejected (no RLS on
     `pg_largeobject`, separate privilege model, easy to orphan).
   The snapshot remains for audit, search ("what did we certify?") and a controlled re-render if a stored file were
   ever lost (the re-render would be flagged as such, never silently served as the original).
6. **Gap-free numbering in Postgres** (`document_sequence`, one counter row per company × type × year):
   - A Postgres `SEQUENCE` is **not** used: `nextval()` is never rolled back, so a failed issue would leave a gap.
   - The issue use case, inside the request transaction and in this order: (a) load and check everything, build the
     snapshot (no lock yet); (b) `insert … on conflict (company_id, document_type_id, year) do update set last_value =
     document_sequence.last_value + 1 returning last_value` — the row lock is held **until commit**, so concurrent
     issuers of the same type and year queue behind it (`lock_timeout` 5 s → 503 `document-busy`); (c) format the
     number, render the PDF with it; (d) insert the register row and the file; (e) record the audit event; commit.
   - Any failure after (b) — rendering error or timeout, constraint violation, process crash, lost connection — rolls
     the whole transaction back, **including the counter**: a number exists only if its register row and PDF exist.
     Invariant (tested): for every company, type and year, `last_value = count(issued_document)` and the sequence
     numbers are exactly `1..last_value`.
   - The price is serialisation per (company, type, year) for the render time (~5–200 ms). HR volumes (tens per day)
     are far below that limit.
   - A voided document keeps its number and row (`status = 'void'`, reason, who, when); numbers are never reused.

## Consequences

**Positive**
- Correct Arabic (shaping, bidi, RTL justification) and French from one engine, verified on the production base
  image, with searchable text and archival PDF/A.
- No new infrastructure, no network at runtime, no extra install on developer machines: the renderer comes from the
  npm lockfile.
- Numbers, register rows and PDFs commit or roll back together; gap-freedom is a database property, not a hope.
- Reprints are byte-identical by construction (stored bytes), independent of later upgrades.

**Negative**
- **+~51 MB** in the API image (binding 50 MB + fonts 1.1 MB) — much less than Chromium (+~760 MB) but not nothing;
  **+~50 MB RSS** per API process once the render process has compiled its first document. The worker entry point
  shares the image; it does not load the renderer unless a job needs it.
- The binding is a third-party wrapper (Myriad-Dreamin/typst.ts) that trails Typst releases. A native crash or an
  out-of-memory abort ends the render process only (amendment below); our templates are fixed code and inputs are
  bounded strings.
- The team learns a little Typst (layout language) for templates.
- Stored PDFs grow the database and the nightly `pg_dump` (≈ 300 MB per 10 000 documents).
- Serialised issuing per type and year (acceptable at HR volumes; revisit only for bulk issuing).

## Alternatives considered

See "Options evaluated". Also rejected: rendering in the web browser (the server must own numbering and the stored
copy); LibreOffice headless with DOCX templates (~500 MB, slow start, non-deterministic output); a hosted PDF service
(violates ADR 005 and offline operation).

## Supersedes

Nothing (the legacy design did not specify document generation).

## Amendment (2026-10-02): render in a child process

The first build ran the binding in a `worker_threads` thread. A thread shares the API process: a Rust allocation
failure inside Typst aborted the **whole API** (seen in a test, documents contract › Settled), and
`worker.terminate()` cannot interrupt native code, so a timed-out render kept its CPU and memory until Typst returned.
The logo pixel limits (2026-09-29) removed the known trigger, not the class of fault.

**Change:** the same binding now runs in a **child process** (`child_process.fork` of `platform/pdf/render-worker`,
IPC with `serialization: 'advanced'`), behind the same `PdfRenderer` port. The engine, fonts, templates and options
are unchanged, so output is identical and the recorded engine version is unchanged.
- A crash or an abort ends the child only: its job fails (`PdfRenderError('error')` → 503), and the next job starts a
  fresh process.
- A timeout sends **SIGKILL**, which really stops native code and frees its memory.
- **Memory ceiling** `PDF_RENDER_MAX_MEMORY_MB` (default 1024): while a render runs, the parent samples the child's
  resident memory every 50 ms (`/proc/<pid>/status`, Linux as in production) and kills it above the ceiling
  (`PdfRenderError('memory')` → 503). It is not checked on other platforms, where a crash is still contained.
- The child gets an **empty environment** (only Node's IPC variables; `SystemRoot` on Windows): no database URL, key
  or secret of the API reaches the renderer.

**Why not the official Typst CLI** (the option named above): a separate binary to download, pin, checksum and install
on Windows dev machines, and a different engine build (reprints are stored bytes, but new documents would change).
Forking the existing binding gets the same isolation with nothing new to install. Cost: one more Node process per
render slot (≈ 50–60 MB RSS once warm, about what the thread used).
